# AuRaw image-quality regression

This directory contains the reproducible RAW-rendering regression layer. It now ships with a compact Bayer/X-Trans corpus, a real headless GPU renderer, pinned reference-engine contracts, deterministic NPZ output, and metric/report generation.

## Canonical renderer output

Every candidate and reference is normalized to the same intermediate:

- NPZ containing `rgb` as little-endian float32, H×W×3.
- Scene-linear D65 Rec.2020 (`linear-rec2020-d65`).
- Full active-area resolution with no resize or output sharpening.
- Before creative look, tone mapping, display encoding, or output ICC conversion.
- JSON metadata in `metadata_json`; the Rust writer stores this as UTF-8 `uint8` for a small, dependency-free writer.

`RawGpuPipeline::read_scene_texture_blocking` provides literal RGBA32F scene-texture readback (alpha is discarded). `RawGpuPipeline::render_regression_scene_blocking` executes the RAW stage and then converts the internal camera-RGB scene into the canonical linear Rec.2020 image. Both APIs require `ProcessingQuality::High` rather than silently widening half-float preview data.

Build and run the real renderer:

```sh
cargo build --locked --release --bin auraw-regression-render

target/release/auraw-regression-render \
  --backend gpu \
  --input regression/raw/synthetic-bayer.dng \
  --output regression/candidates/synthetic-bayer-multitarget.npz
```

The NPZ writer uses stored ZIP members, fixed timestamps and deterministic NPY headers. Rendering the same scene twice is therefore suitable for both pixel and whole-file reproducibility checks.

## Checked-in Bayer and X-Trans corpus

`corpus.yaml` enables two CC0 fixtures generated by `generate_synthetic_corpus.py`:

- `synthetic-bayer.dng`: RGGB Bayer.
- `synthetic-xtrans.dng`: a true repeating 6×6 X-Trans CFA.

Both encode the same multi-target scene: a neutral slanted edge, difficult textile/frequency detail, an underexposed noisy flat field, and colored/neutral clipped highlights. The manifest pins the DNG SHA-256 values and defines edge, neutral, frequency, noise, and highlight ROIs.

Validate the committed bytes and coverage:

```sh
python3 scripts/image_regression.py validate-corpus \
  --manifest regression/corpus.yaml --verify-files
```

Regenerate them only as a reviewed corpus change:

```sh
python3 regression/generate_synthetic_corpus.py
python3 scripts/image_regression.py validate-corpus \
  --manifest regression/corpus.yaml --verify-files
```

A regeneration must reproduce the hashes already in `corpus.yaml`; otherwise update the generator version, manifest hashes, and baseline review together.

## Pinned darktable and Ansel histories

`reference-engines.yaml` pins:

- darktable 5.6.0 / release `release-5.6.0`, including the release-source SHA-256.
- Ansel rolling release at commit `17343ac785c067be88b33ba141c5a80bdcaab1b6`.
- A hashed, audited processing-history contract for each engine.

The history contracts under `profiles/` enumerate active-area/orientation handling, camera white balance, guided highlight reconstruction, fixed Bayer and X-Trans demosaic choices, disabled denoise/creative modules, Rec.2020 working/output profiles, and float32 linear TIFF export. They are reviewable module-stack contracts, not invented version-dependent XMP parameter blobs. A reference-export wrapper must implement the contract in the pinned engine and should retain the engine-generated XMP/style beside the resulting baseline.

Validate pins and history hashes without requiring either application:

```sh
python3 scripts/image_regression.py validate-reference-engines \
  --config regression/reference-engines.yaml
```

Validate installed binaries as well:

```sh
python3 scripts/image_regression.py validate-reference-engines \
  --config regression/reference-engines.yaml --verify-binaries
```

Reference rendering requires the pin file. The command template also receives `{history}`, so an audited wrapper can consume the selected contract:

```sh
python3 scripts/image_regression.py render \
  --manifest regression/corpus.yaml \
  --backend darktable \
  --reference-engines regression/reference-engines.yaml \
  --command-template 'scripts/render-darktable-reference.sh {history} {raw} {output}' \
  --output-root regression/reference-tiff/darktable \
  --extension .tif
```

The render manifest records the exact engine version output, source revision, source checksum when available, history path, history checksum, deterministic environment, output hashes, and elapsed time. A version mismatch aborts before rendering.

Normalize a pinned reference TIFF set:

```sh
python3 scripts/image_regression.py normalize-corpus \
  --manifest regression/corpus.yaml \
  --input-root regression/reference-tiff/darktable \
  --output-root regression/references/darktable \
  --extension .tif --transfer linear \
  --reference-engines regression/reference-engines.yaml \
  --reference-engine darktable
```

Never label a display-referred TIFF as linear. Reference updates must review the engine pin, generated sidecar/style, history-contract hash, export profile, and image deltas.

## Measurements

`compare_images` reports:

- Linear RMSE, MAE, maximum absolute error, and PSNR.
- CIEDE2000 mean, p95, and maximum ΔE.
- Scharr edge magnitude RMSE, p95 edge-response error, median response-gain error, and p95 direction error.
- Chroma-Laplacian zippering and neutral-edge false color.
- Robust per-channel flat-field noise sigma, relative noise change, and residual bias.
- Highlight ΔE, maximum channel error, relative luminance RMSE, p99 peak error, and clipped-area fraction change.

ROIs in `corpus.yaml` select the appropriate target for each metric. `thresholds.yaml` supplies global, tag-specific, backend-specific, and direct CPU/GPU limits.

## Deterministic GPU smoke test

On a machine with LibRaw and a wgpu adapter (a Mesa software Vulkan adapter is sufficient):

```sh
cargo build --locked --bin auraw-regression-render
scripts/smoke-regression-renderer.sh
```

The script validates the corpus and reference pins, renders both CFA fixtures twice, requires bit-exact pixels, and loads every Rust-written NPZ through the Python harness.

The general runner can render any selected scenes:

```sh
python3 scripts/image_regression.py render \
  --manifest regression/corpus.yaml --backend gpu \
  --command-template 'target/release/auraw-regression-render --backend gpu --input {raw} --output {output}' \
  --output-root regression/candidates/gpu --repeat 2

python3 scripts/image_regression.py determinism \
  --manifest regression/corpus.yaml --backend gpu \
  --run-a regression/candidates/gpu/run-1 \
  --run-b regression/candidates/gpu/run-2 \
  --max-abs 0 --report regression/reports/gpu-determinism.json
```

## Comparison and reports

Compare AuRaw against a pinned baseline:

```sh
python3 scripts/image_regression.py compare \
  --manifest regression/corpus.yaml \
  --thresholds regression/thresholds.yaml \
  --reference-root regression/references/darktable \
  --candidate-root regression/candidates/gpu/run-1 \
  --backend gpu --reference-engine darktable \
  --reference-engines regression/reference-engines.yaml \
  --report-dir regression/reports/gpu-vs-darktable
```

Compare independently rendered CPU and GPU outputs directly:

```sh
python3 scripts/image_regression.py cpu-gpu \
  --manifest regression/corpus.yaml \
  --thresholds regression/thresholds.yaml \
  --cpu-root regression/candidates/cpu/run-1 \
  --gpu-root regression/candidates/gpu/run-1 \
  --report-dir regression/reports/cpu-gpu
```

Every candidate NPZ must attest its backend, immutable source revision, RAW
SHA-256, renderer-executable SHA-256, implementation identifier,
implementation fingerprint, color space, and transfer function. The harness
rejects command-line/backend disagreement, unknown revisions, changed input or
renderer hashes, mismatched source revisions, and CPU/GPU pairs that share an
implementation identity, fingerprint, or executable hash. Determinism checks
also require identical provenance across runs before comparing pixels.

The repository currently ships the canonical GPU renderer only. Therefore a
successful GPU/reference comparison is not evidence of CPU/GPU parity. The
`cpu-gpu` command becomes meaningful only when a separately built and hashed
CPU renderer emits the same provenance contract; until then CI must not report
CPU/GPU parity as proven.

Each comparison writes JSON, JUnit XML, and HTML. CI retains renderer manifests
and reports. Threshold changes and baseline changes are reviewed source
changes, never an automatic overwrite from a candidate build.
